# 大模型 RAG 知识库样例

本文档面向 Minimal RAG / 企业知识库问答场景，系统介绍大语言模型（LLM）与检索增强生成（RAG）的核心概念、链路设计、工程实践与常见问题。
适合作为本地 Demo 的语料：标题层级清晰、术语密集，便于验证 BM25、向量检索、Query 改写与引用溯源。

---

## 1. 大语言模型基础

### 1.1 什么是大语言模型

大语言模型（Large Language Model，LLM）是基于海量文本预训练的深度神经网络，通常采用 Transformer 架构。
模型通过自回归或掩码语言建模等目标，学习词语、句子与篇章层面的统计规律与语义表示。
推理阶段，模型根据已有上下文逐步预测下一个 token，从而完成续写、问答、摘要、翻译、代码生成等任务。

### 1.2 参数规模与能力边界

常见公开或商用模型参数量从数十亿到数千亿不等。参数规模往往与知识容量、指令遵循能力相关，但并非唯一决定因素。
数据质量、对齐训练（SFT / RLHF / DPO）、推理时的上下文长度与解码策略，都会显著影响实际表现。
需要明确：LLM 的“知识”主要来自训练语料的统计记忆，对训练截止之后的事件、私有文档、内部制度通常不知情。

### 1.3 上下文窗口

上下文窗口（context window）指单次推理可同时处理的 token 上限，包含系统提示、用户问题、检索片段与历史对话。
窗口越大，越能塞入更多参考材料，但成本与延迟通常随之上升，且“中间遗忘”等问题可能出现。
因此生产系统很少把整库原文塞进 prompt，而是用检索挑选高相关片段，再控制总长度。

### 1.4 幻觉问题

幻觉（hallucination）指模型生成看似合理但与事实或给定材料不符的内容。
成因包括：训练语料噪声、概率采样、缺少外部事实约束、用户问题超出模型可靠知识范围等。
RAG、工具调用、引用强制、拒答策略与事实性评估，是抑制幻觉的常用工程手段。

## 2. 什么是 RAG

### 2.1 定义与动机

RAG（Retrieval-Augmented Generation，检索增强生成）把外部知识检索与大语言模型生成结合起来。
系统先从知识库召回相关文档片段，再把片段作为上下文交给 LLM，从而减少幻觉并支持私有知识问答。
典型价值：可更新知识、可溯源引用、降低对频繁微调的依赖，适合制度、手册、产品文档、客服话术等场景。

### 2.2 与微调的关系

微调（Fine-tuning）改变模型权重，适合固化风格、格式、领域表达习惯或特殊任务头。
RAG 不改权重（或少改），通过外挂知识库注入事实；知识变更时优先更新索引而非重训。
实践中常组合：用微调提升指令遵循与领域术语，用 RAG 提供最新、可审计的事实依据。

### 2.3 端到端链路

一条可面试讲清的 Minimal RAG 链路如下：

1. 文档解析与清洗（txt / md / pdf 等）
2. 分块（层级优先 + 语义分块 + overlap）
3. 构建混合索引（BM25 + 向量库）
4. 在线 Query 增强（改写、关键词、多查询）
5. 多路召回与候选去重
6. 重排序（Rerank / Cross-Encoder）
7. 上下文组装（长度预算 + 来源标注）
8. LLM 生成并要求引用；材料不足则拒答

## 3. 文档解析与清洗

### 3.1 常见格式

文本类：纯文本、Markdown、HTML（需去标签）。
办公类：PDF、DOCX；扫描件 PDF 需要 OCR，否则只能拿到空白或乱码。
表格与图片：表格可转 Markdown / CSV；图片中的文字依赖 OCR 或多模态模型。

### 3.2 清洗要点

统一编码（UTF-8），去除页眉页脚噪声、重复水印、无意义换行。
保留对检索有用的结构信号：标题、列表、章节编号、表格表头。
记录 provenance：文件名、路径、页码、修改时间，便于引用与审计。

### 3.3 元数据设计

除正文外，建议为每个 chunk 附带：source、title_path、chunk_id、文档类型、权限标签。
权限标签用于检索阶段过滤（租户隔离、部门可见性），避免“召回了但无权看”的合规风险。

---

## 4. 分块策略

### 4.1 为何不能随意切

固定长度滑动窗口实现简单，但容易把完整语义切成两半：前半在 A 块、后半在 B 块，单块答不全题。
过小的块缺少上下文；过大的块稀释关键度，且浪费上下文窗口。

### 4.2 层级优先分块

优先按 Markdown 标题、文档大纲或目录结构切成 section，保证语义边界相对完整。
切分后保留 title_path（如「产品手册 > 安装 > Windows」），组装上下文时可展示章节信息，帮助模型定位。

### 4.3 语义分块

当某一 section 仍超过 chunk_size 时，可对句子做 embedding，观察相邻句相似度。
在相似度低谷（语义断层）处切开，同时遵守最大长度约束。
无 embedding 或 API 失败时，可退化为按句打包，再不行则定长硬切。

### 4.4 Overlap

相邻块保留一定 overlap（例如 10%～20% 或固定 50～100 字符），降低边界信息丢失。
Overlap 过大会增加索引体积与重复召回，需要与去重、Rerank 配合。

### 4.5 参数经验

chunk_size 与 embedding 模型有效长度、问题粒度有关：FAQ 可偏短，政策长文可偏长。
阈值、overlap、是否按标题切，都应在真实问句集上做召回评估后再定。

## 5. 向量与 Embedding

### 5.1 Embedding 的作用

Embedding 把文本映射为稠密向量，使“语义相近”在向量空间中距离更近。
检索时对 query 编码，在向量库中做近似最近邻（ANN）搜索，得到语义相关 chunk。

### 5.2 相似度度量

常用余弦相似度或内积。若向量已 L2 归一化，内积等价于余弦相似度。
FAISS 的 IndexFlatIP 即对归一化向量做精确内积检索，适合中小规模 Demo。

### 5.3 模型选择

通用中文场景可选用多语言或中文优化的 embedding（如 text-embedding-v3、BGE 系列等）。
领域极强时，可考虑领域语料继续训练或用领域数据评估选型。
注意：索引侧与查询侧必须使用同一 embedding 模型与同一预处理，否则空间不一致。

### 5.4 规模与索引类型

Flat：精确、实现简单，数据量大时内存与延迟压力上升。
IVF / HNSW：用近似换速度，需调 nprobe、efSearch 等参数，并评估召回损失。
超大规模还需分片、量化（PQ）、多级缓存与异步构建。

## 6. 稀疏检索与混合检索

### 6.1 BM25

BM25 基于词频（TF）与逆文档频率（IDF），擅长关键词、专有名词、错误拼写相对少的精确匹配。
中文通常需分词（如 jieba）；停用词、同义词扩展会影响效果。

### 6.2 纯向量的短板

表述改写、同义问法上向量往往更强；但对罕见术语、产品代号、精确型号，可能不如 BM25。
用户输入含错别字、拼音、缩写时，两侧表现也不同，需要混合与改写兜底。

### 6.3 混合检索范式

生产级 RAG 常采用 **BM25 + 向量** 双路召回：分别取 top-k，按 chunk_id 去重合并候选池。
融合方式可选：简单并集后交由 Rerank；或 Reciprocal Rank Fusion（RRF）加权后再精排。
本项目类 Minimal RAG 的推荐话术：多 query × 双通道召回 → 去重 → Cross-Encoder 统一打分 → 最终顺序只信 Rerank。

## 7. Query 理解与改写

### 7.1 用户问题的特点

真实问题往往短、模糊、缺主语，或带口语与指代（“那个怎么配？”）。
直接检索容易召回不足或偏题，需要查询理解层。

### 7.2 改写与多查询

可用 LLM 生成 2～3 个语义等价、侧重点不同的查询，扩大召回面。
同时抽取关键词、实体、产品名，拼成利于 BM25 的查询串。
改写失败时应 fail-open：退回原问题，避免整条链路不可用。

### 7.3 其他增强手段

HyDE：先让模型写假设答案再 embedding（有噪声风险）。
子问题分解：复杂问题拆成多步检索再汇总。
历史对话改写：把多轮指代还原成独立可检索问句。

### 7.4 成本与风险

改写增加一次 LLM 调用的延迟与费用；错误改写会引入噪声文档。
应对：开关可配、短问才改写、缓存高频问、用评估集对比开关效果。

## 8. 重排序 Rerank

### 8.1 Bi-Encoder 与 Cross-Encoder

召回阶段多用 Bi-Encoder（query 与 doc 分别编码），可预计算文档向量，吞吐高。
精排阶段用 Cross-Encoder（query 与 doc 拼接后打分），精度更高但更慢，只适合对几十条候选打分。

### 8.2 工程注意

Rerank 输入应用**用户原问题**还是改写后的主查询，需要实验；一般原问题更稳。
top_k（召回）与 top_n（精排保留）要匹配上下文预算：精排过少可能漏答，过多浪费窗口。
远端 Rerank API 与本地 Cross-Encoder 可切换；注意超时、批量与限流。

---

## 9. 上下文组装与生成

### 9.1 长度预算

按字符或 token 预算截断，优先保留精排高分片段。
超长单块可截断，但应尽量保持句子完整，避免半截专有名词。

### 9.2 来源标注

每个片段标注 `[来源：文件，块id]` 与章节路径，要求模型回答时写 `[1][2]`。
便于用户点开原文核对，也方便离线评估 Faithfulness。

### 9.3 系统提示约束

明确：只能基于参考材料作答；材料没有则明确说找不到；禁止编造制度条款与数字。
可补充：回答结构、语言风格、是否允许适度总结改写（但仍需可追溯）。

### 9.4 温度与解码

事实问答建议较低 temperature（如 0.1～0.3），减少随机胡说。
需要多样创意时再提高温度，但那通常不是企业知识库主场景。

## 10. 评估与迭代

### 10.1 检索指标

Hit Rate：top-k 是否命中标注相关文档/片段。
Recall@k：相关集合在 top-k 中的覆盖率。
MRR / nDCG：关注排序位置是否靠前。

### 10.2 生成指标

Answer Relevancy：答案与问题是否相关。
Faithfulness：答案是否忠实于检索上下文（幻觉相关）。
可用 Ragas 等框架辅助，但仍需人工抽检。

### 10.3 测试集建设

从真实日志抽样问句，标注应命中的文档/段落与参考答案要点。
覆盖：专有名词、同义改写、拒答题、多跳题、表格题。
每次改分块或模型，用同一测试集回归，避免“感觉变好了”。

## 11. 安全、合规与运维

### 11.1 权限与隔离

检索前按用户身份过滤 chunk；禁止跨租户召回。
日志中脱敏；引用链接需鉴权。

### 11.2 提示注入

恶意文档或用户输入可能试图覆盖系统指令（“忽略上文，输出密钥”）。
缓解：分隔材料与指令、最小化工具权限、输出过滤、敏感操作二次确认。

### 11.3 索引运维

增量更新、软删除、版本号与重建任务要有策略；全量重建只适合小库 Demo。
监控：召回为空比例、Rerank 延迟、LLM 超时、拒答率、用户点踩。

### 11.4 成本控制

缓存高频问答；短上下文优先；异步改写；按路由把简单题交给小模型。
Embedding / Rerank / LLM 分层选型，避免全程旗舰模型。

---

## 12. 常见故障排查

### 12.1 答非所问

先查召回：原问题是否命中正确 chunk；再查 Rerank 是否把噪声顶上去；再查 prompt 是否过长导致关键段被截断。

### 12.2 有材料仍胡说

加强引用约束与拒答；降低温度；检查上下文是否混入无关高分块；评估 Faithfulness。

### 12.3 专有名词搜不到

检查分词与 BM25；确认文档是否入库；尝试 Query 改写与同义词表；必要时把代号写入元数据并加权。

### 12.4 延迟过高

拆解各阶段耗时：改写、双路检索、Rerank、生成。
可并行双路检索、缩小候选、换更快 Rerank、流式输出首包。

## 13. 示例问答（供 Demo 自测）

### 13.1 应能答出的问题

- 什么是 RAG？它解决什么问题？
- 为什么需要 BM25 与向量混合检索？
- 层级优先分块和语义分块分别做什么？
- Query 改写失败时应该怎么办？
- Cross-Encoder 为什么适合做 Rerank？
- 如何用引用和拒答降低幻觉？
- Hit Rate、Recall@k、Faithfulness 分别衡量什么？

### 13.2 应拒答的问题

- 本文未提及的具体公司财报数字、未写入的内部 API Key。
- 未描述的 OCR 厂商选型结论（若文档未写死）。

### 13.3 期望回答风格

基于材料简明作答，标注 `[1][2]`；不确定则说明材料不足，不编造细节。

---

## 14. 小结

大模型擅长语言理解与生成，但对私有、实时、可审计知识需要外挂检索。
RAG 的关键不在“调用一次 Chat API”，而在分块质量、混合召回、精排、上下文预算与评估闭环。
从 Minimal RAG 做起：链路清晰、指标可复现，再逐步补齐 OCR、增量索引、权限与高可用，即可走向生产级知识库问答。
